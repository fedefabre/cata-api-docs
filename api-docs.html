CATA Render Service (11.0.0)

Download OpenAPI specification:

Federico Fabre: federicofabre@gmail.com

Asynchronous, job-based render service for the CATA virtual try-on app.

Consumed by the Core Backend as the sole external caller. The Flutter client does not call this API directly — it goes through Core.

Composing a look

A render is one garment on one avatar. An outfit is not generated: it is composed by the client from renders it already has.

Every render of a user starts from the same canonical avatar, so all of them are registered to identical pixels. Alongside each render the service stores a layer (the region that render changed, cut out) and a claim mask (which of those pixels are the garment's own fabric rather than the area the previous garment occupied). Both are returned by /assets/garment-avatar-render/latest.

To dress an avatar, fetch one render per garment and draw: the avatar, then the layers, then each garment's claim. No call to this service is involved in building a combination, so any number of outfits from a wardrobe costs nothing after the individual renders exist.

The stacking rules and their rationale are in the architecture document (§10.18). A 404 from the render endpoint is not an error: it means no render exists at the recipe currently in force, and the garment needs rendering again.

Not in this contract

The running service exposes a few endpoints and fields that are deliberately absent here, because they are scaffolding for internal tools rather than product surface: short-lived signed viewing URLs (assets will be served as stable public CDN URLs), a queue/worker status endpoint, an upload helper, and the internal per-avatar artefacts used by the render pipeline itself (face mask, silhouette, pose keypoints). Do not build against them. The background-free avatar is the exception: it exists for display rather than for the pipeline, so it is documented and safe to build against.

Ownership boundary

Domain Core Backend Render Service
User identity, auth issuance ✅ source of truth (Supabase) validates JWT only
Product / garment metadata (catalog, attributes, lifecycle) ✅ source of truth thin reference (garment_id only)
Avatar metadata + active avatar state ✅ source of truth thin mirror (user_id, active_avatar_id, avatar_v)
Source asset bytes (uploads) ✅ stores in CDN reads by URL/ID
Jobs, processed assets, renders, recipe runs — ✅ source of truth
Render-specific state (versions, recipes, lifecycle) — ✅ source of truth

The Render Service holds thin references, not authoritative copies, of Core-owned entities. Garment and avatar metadata lookups beyond what is needed for job execution and version-aware retrieval go to Core, not Render.

URL immutability and caching

Every CDN URL returned by this API is immutable — once an asset is produced at a given version, its URL never changes. New versions are published at new URLs; old URLs continue to serve the bytes they were minted with. Callers may cache any URL indefinitely without coordination.

The only thing that changes over time is which URL is returned by the /assets/.../latest endpoints. A caller treating those endpoints as a short-TTL cache lookup is the recommended pattern.

Common flows

Garment upload: Core uploads source bytes to its CDN, then POST /jobs { type: "garment_processing", ... }. Polls GET /jobs/{id} until status: "completed"; reads the processed asset URL from outputs.

Job chaining: completions can trigger follow-on jobs automatically (the orchestrator's rule set — see architecture.md §4.4). In particular, when a garment_processing job completes and the user's active avatar has a processed asset, the service automatically enqueues the first garment_avatar_render — Core should not create that render itself. If no avatar is active yet, the garment is rendered later by avatar_backfill when one becomes active. Core fires a render job only for a genuine miss at Fitting Room read time (below).

Fitting Room load: Core calls POST /assets/garment-avatar-render/batch with the user and the list of garments. The endpoint returns the latest URL per pair, or not_found for pairs that haven't been rendered yet. For misses, Core fires individual or batched render jobs and tells Flutter "rendering".

Caching responsibility lives on the device, not in Core. Every CDN URL returned is immutable (see above), so Flutter's standard image cache (e.g. cached_network_image) keyed by URL handles "fitting room feels instant on revisit" with no infrastructure work. Core should call the /batch endpoint on every fitting-room load; the endpoint is sized for it.

Avatar approval and change: processing an avatar does not make it active — the user must see the canonical avatar and accept it first, because activating a new avatar invalidates every render they already have. avatar_backfill is that approval signal as well as the activation one: when the user accepts a processed avatar, or activates an already-processed one, Core signals it with POST /jobs { type: "avatar_backfill", inputs: { user_id, new_active_avatar_id, new_avatar_v } }. Activation is refused silently (the job still succeeds; read outputs.activation) if the avatar has no processed asset yet or its version does not match the one signalled. When a newly-uploaded avatar finishes avatar_processing and becomes active, the render service auto-chains the backfill itself, so Core must not also POST it in that case. Both paths dedup on (user_id, new_active_avatar_id, new_avatar_v), so an accidental double-signal produces only one fan-out. Render fans out child render jobs for the user's wardrobe; pending renders against the previous avatar version are marked superseded. Core polls the parent job for the children list.

See architecture.md for the full production architecture, supersession mechanics, and decision rationale.

Bulk lookup of latest renders

The Fitting Room read path. Returns the latest valid render for each (user_id, avatar_id, garment_id, view_assumptions) query in a single round trip. Sized for the common case where a Fitting Room load needs URLs for many garments against the user's active avatar.

Per-query result is either found (with the render) or not_found (caller may fire a garment_avatar_render job for that pair, or use POST /jobs/batch to fire several at once). Read-only — this endpoint never creates jobs.

This endpoint is read-only and never blocks on generation. If a lookup finds an asset produced under an older recipe version it may enqueue a single background regeneration, but the response is immediate and it never creates a synchronous render job.
